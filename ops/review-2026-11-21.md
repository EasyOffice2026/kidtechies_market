# What went wrong, and what was built to fix it

The question asked on 2026-11-21 was the right one: the "marketing agent" does
not do the marketing. It writes drafts. This review explains how that
happened, what else is blocking results, and what was built on the same day to
close the gaps that code can close.

## Summary

The agents work: they draft safely, and they pass their tests. **But no draft
has reached a parent in nine weeks.** There are four reasons. The scope
stopped short of marketing. Most of what the agents write had nowhere to be
published. One client approval (D1) blocks everything, and nobody owns
getting it done. And approval was a convention, not a control.

Two of those can be fixed in code, and were (section 3). The other two need
decisions from the client (section 4).

## 1. What went wrong

### 1.1 The scope stopped before marketing — and the name promised more

The specification (KT/DEV/2026-001) defines Stage 1 as **no-code drafting**:
agents prepare work, a person approves it, **publishing stays manual** until a
later Stage 2. It also excluded the marketing programme itself, Growth
Dossier sections 04–07: the channels, the campaigns and the numbers.

That was recorded on 2026-09-21 (`ops/five-day-plan.md`: "this engagement
delivers the machine that produces the marketing, not the marketing programme
itself"). But it was never the headline the client heard. A system called
"AI Marketing Agent" reads as one that markets. **The gap between the name and
the scope is the root of the disappointment, and it should have been put to
the client in plain words at the start.**

### 1.2 Three of the four things the agents write had nowhere to go

The Content Factory writes four things per package. Here is where each one
could actually be published, as of this morning:

| Output | Where it could go | Reality on 2026-11-21 |
|---|---|---|
| 800–1,000-word article | The site's articles section — GTM Phase 2's "SEO layer" | **The site had no articles section.** No page existed to put one on |
| Five social captions | Instagram, Facebook, LinkedIn, TikTok | **No company accounts are set up.** The site's social links are all empty (`NEXT_PUBLIC_INSTAGRAM` etc.) |
| Nurture email | The parent mailing list | The list sends its own fixed welcome emails and the weekly question. **There is no place for an agent email in it** |
| Video hook | TikTok / Reels | No accounts; nobody assigned to film |

So even with D1 signed, most of the output would have had no destination.
Nobody checked that end-to-end route — draft, approval, channel, parent —
before building the agents.

### 1.3 Very little has been written, and none of it published

| | Planned | Actual |
|---|---|---|
| Content Factory runs since 2026-09-18 | 3 a week, about 27 | **2 packages** (queue items 1 and 1b) |
| Queue items ready and unwritten | — | **14** |
| Posts published | GTM Phase 2 (5 Nov – 4 Dec): message testing under way | **0.** Phase 2 has not started |
| Real visitors | — | **0.** Every visit so far is the team's own testing |

Most of the delay came from setup on the client's account. Scheduled tasks
were proven only on 2026-11-12 (D4). The first Content Factory run on the
client's account was 2026-11-16.

### 1.4 One approval blocks everything, and nobody owns it

`knowledge/product-facts.md` is still **0.8.4-DRAFT**. Until the client
approves the fact list (**D1**), every rule in the system correctly says
"nothing is published". **D14** — who approves drafts each morning — is also
open. Every safeguard enforces the wait. Nothing pushes the decision to a
close, and the GTM plan's owner (D9) is also unassigned.

### 1.5 Approval was a typed line, not a control

The approver typed `approved-by: Name date` into a file by hand. Nothing
checked that the file had not changed afterwards. Nothing stopped someone
from posting a draft that was never approved. And the publishing log relied
on someone remembering to fill it in. **The safety model was discipline.** The
specification's own Stage 2 data model would have double-published after a
timeout (found in analysis, `ops/five-day-plan.md`).

### 1.6 Measurement needs a developer every Thursday

The Funnel Analyst can only run if someone does the following each week:

- reads four numbers off the Umami dashboard
- runs the export in the product repo
- copies two files to the client's computer before Friday 09:00

On Umami's free plan none of that is automatic. Today it is the developer's
job.

### 1.7 Development effort went to precision, not reach

The three audit rounds of 2026-11-20 corrected wording across 112 product
files and more than 100 marketing files. That work matters for a children's
product: a wrong privacy sentence is a real harm. **But it was the wrong
priority while there was still no route from a draft to a parent.**

## 2. What is not wrong

- **The agents do what they were built to do.** The safety tests passed 8/8 on
  the client's account (2026-11-19), and the drafts are usable.
- **The funnel exists**: free mission → email list → six emails → purchase,
  live and tested end to end since 2026-11-07, and measured since 2026-11-09.
- **The safety rules are right.** Nothing here argues for loosening them. It
  argues for enforcing them in code, which section 3 does.

## 3. What was built on 2026-11-21

### 3.1 A publishing destination: "Guides for parents" on the site

Product repo, branch `feature/guides`, built on `fix/review-round-1`. It is
**not merged and not deployed**.

- **`/guides` and `/guides/<slug>`**: approved articles become pages on
  kidtechies.com, with a proper title, description, canonical URL, Article
  structured data, and a sitemap entry. This is the SEO channel the GTM plan
  counts on, and it needs no outside account.
- **A publishing gate in code** (`scripts/lib/guides.mjs`), run by
  `npm run build:guides` and `check:guides`. It refuses a guide that:
  - has no approval record;
  - was approved against a DRAFT fact list;
  - still carries the agents' "not yet client-confirmed" notice;
  - has more or fewer than one free-mission link;
  - links to any of our own pages other than a story or another guide (a
    second call to action);
  - contains a sentence the claims file forbids;
  - uses anything beyond safe text formatting (HTML, images, tables).

  One refused file stops the whole build.
- **Hidden while empty.** Until the first guide is published, `/guides` is a
  404 and the footer link and the sitemap entry do not appear. The branch is
  safe to merge before D1.
- **Verified:**
  - 37 gate checks pass.
  - Type-check, lint and every unit check pass.
  - The bundle, page and API checks pass.
  - A sample guide was published through the tool, built and served:
    - the page returned 200;
    - unknown slugs returned 404;
    - the page had exactly one free-mission link;
    - outside links opened safely;
    - the footer and sitemap entries appeared.

    The sample was then removed, and the empty state was checked again.

### 3.2 Approval and publishing enforced in code: `tools/kt.mjs`

The core of Stage 2 is now in this repository: the approval gate, the state
model and the publish log, all as code. It needs no new service and no
external accounts, and has no dependencies beyond Node.js.

| Command | What it does |
|---|---|
| `kt status` | Every publishable draft: waiting, approved, changed since approval, published. Lists anything that needs a person first |
| `kt check <draft>` | The knowledge-base checks: DRAFT facts, the draft notice, forbidden claims, one call to action per piece, prices not in the fact file |
| `kt approve <draft> --by <name>` | Runs the checks. Refuses on any problem, and refuses an agent's name. Writes the `approved-by:` line and a ledger record with the file's hash, the fact-list version and the computer account |
| `kt publish <article> --to guides --site <repo>` | Article → site guide. Refuses without an approval that matches the file as it is now. Runs the site's own gate before writing, never overwrites, and fills the publishing log |
| `kt post <draft> --channel instagram --piece "Instagram 1"` | For channels without an API connection yet: prints the exact approved copy to post, and records it as being published |
| `kt confirm <id> --url <link>` / `kt cancel <id>` | Closes the loop and writes the publishing-log row |
| `kt resolve <id>` | The only way out of `PUBLISH_UNKNOWN` |

It also carries the fixes Stage 2 always needed:

- **States:** APPROVED → PUBLISHING → PUBLISHED, with FAILED and CANCELLED.
- **No automatic retry after a part-way failure.** That case becomes
  `PUBLISH_UNKNOWN`, and only a person can clear it.
- **One publication per draft, channel and caption.**
- **Edits cancel approval.** Changing a file after approval cancels the
  approval.
- **DRAFT facts block everything** except a clearly marked rehearsal, which
  can only dry-run.

**Tests:** `npm test`, 27 tests, all passing, including the full route into a
real copy of the site's gate.

### 3.3 What did not change

The agents still only draft. The tool is run by a person. One rule was added
to `agents/shared-controls.md` §2: an agent never runs the tool or writes its
records. Test case 6.5 (`tests/cases.md`) checks it on the next run. No agent
prompt changed, and the skill does not need re-uploading for this.

## 4. What only the client can unblock

In order. Each one opens up the next:

1. **D1 — approve the fact list.** Until then the tool and the site both refuse
   to publish, by design.
2. **D14 — name the approver.** One person, 20 minutes a day, running
   `kt approve`.
3. **Create the company accounts:** Instagram, Facebook page, LinkedIn page and
   TikTok. Put their links in Vercel (`NEXT_PUBLIC_INSTAGRAM` and the others)
   so the site shows them. Without accounts, captions have nowhere to go.
4. **Decide where `kt publish` runs.** It needs the agent folder and the
   product repo on the same computer. Either:
   - clone the product repo on the client's computer, or
   - the developer runs it once a week.
5. **Install Node.js 20 or later** on the client's computer, so the approver
   can run `kt` there. This is a one-off install.
6. **D16 — the ad budget,** for the GTM Phase 2 message tests.

## 5. Next, in code, once accounts exist

- **Direct posting** for the one or two channels that turn out to matter
  (Stage 2 connectors). Meta's API needs a business-verified app and a review.
  LinkedIn needs page-admin rights. TikTok's posting API needs an audit. Each
  needs the account first, which is why none was built today.
- **An optional `meta_description:` line in the Content Factory's article
  front matter**, so the page description is written for search, not taken
  from the first sentence. This is an agent prompt change, so it re-runs test
  class 1.
- **Deploy `feature/guides`** together with, or after, `fix/review-round-1`.
